# AFB Domain Language

> Status: Draft (rev 1)
> Date: 2026-04-26
> Companion: architecture.md, spec.md

Terms used throughout AFB documentation and code. Canonical definitions. If a term is used inconsistently, this document wins.

## Core Concepts

| Term | Definition | Owned by |
|------|-----------|----------|
| **Manifest** | `afb.toml` — declarative description of desired harness state. Source of truth for what should exist | User |
| **Local manifest** | `afb.local.toml` — user-specific overrides, deep-merged over manifest. Gitignored | User |
| **Lockfile** | `afb.lock` — records exact resolved state (versions, commit hashes, image digests). Committed. Enables reproducibility | AFB (generated) |
| **Harness** | The complete agent development environment: runtime(s), tools, composed config, container image. One harness per project | — |
| **Component** | External tool managed by AFB via lifecycle hooks (install, version, doctor, user-defined commands). Opaque — AFB runs hooks without understanding what the component does | User + component |
| **Layer** | A source of config files (git repo or local directory) with an integer priority and a merge strategy. Layers compose to produce the final config in `.ai/` | User |
| **Project config** | `.afb/project/` — the implicit highest-priority layer. Committed to the project repo. Contains the same types of files as external layers (rules, skills, settings) | User |
| **Target** | A runtime that receives generated config (Claude Code, OpenCode, Codex). LNAI translates composed config into target-native formats | — |
| **Template** | An `afb.template.toml` file or git repo used to scaffold a new manifest via `afb init --template`. Template source and ref are recorded in manifest for drift detection | User |

## Processes (Verbs)

| Term | Definition | CLI command |
|------|-----------|-------------|
| **Init** | Scaffold a new project: create `afb.toml`, `.afb/project/`, gitignore entries. Optionally from a template | `afb init` |
| **Compose** | Merge layers by priority into a single config directory (`.ai/`). Higher priority wins on conflict. Standalone operation, also part of Apply | `afb compose` |
| **Apply** | Compose layers, validate, then run the configured sync command (default: `lnai sync`) to translate `.ai/` into target-native configs. Updates lockfile. The full declarative pipeline | `afb apply` |
| **Build** | Generate Containerfile + compose.yaml from manifest, then build the container image | `afb build` |
| **Up** | Start containers from built image via compose | `afb up` |
| **Down** | Stop and remove containers via compose | `afb down` |
| **Rebuild** | Build + down + up. Convenience command for applying manifest changes to running containers | `afb rebuild` |
| **Lock** | Resolve exact versions, commit hashes, and image digests. Write to `afb.lock` | `afb lock` |
| **Doctor** | Diagnostic check. Inside a project: check lockfile freshness, config drift, run component doctor commands. On host: check AFB prerequisites | `afb doctor` |
| **Diff** | Detect divergence between declared state and actual state at two levels: composition drift and runtime drift | `afb diff` |
| **Validate** | Check manifest schema validity and composed `.ai/` directory validity (delegates to `lnai validate`). Runs after compose, before the sync command | `afb validate` |
| **Run** | Execute a script from `.afb/scripts/` or a component command (`component.command` format) | `afb run` |
| **Push** | Push changes in layer dir(s) to upstream git, update manifest pin | `afb push` |
| **Layer Pull** | Git pull in specified (or all) layer dirs. Respects `ref` pin | `afb layer pull` |

### Terminology: Apply vs Sync Command

**Apply** (`afb apply`) is AFB's operation: compose + validate + run sync command + update lockfile.

**Sync command** refers to the external tool configured in `[sync].command` (default: `lnai sync`). It translates composed `.ai/` into runtime-native formats. The sync command is one step within Apply — not the same thing.

Use "apply" for AFB's operation, "sync command" for the external tool invocation.

## Artifacts

| Term | Location | Committed? | Description |
|------|----------|-----------|-------------|
| **Manifest** | `afb.toml` | Yes | Desired state |
| **Local manifest** | `afb.local.toml` | No | User overrides |
| **Lockfile** | `afb.lock` | Yes | Resolved state |
| **Composed config** | `.ai/` | No | Merge output, gitignored |
| **Runtime configs** | `.claude/`, `.opencode/`, `.mcp.json` | No | Generated by sync command, gitignored |
| **Containerfile** | `.afb/generated/Containerfile` | No | Generated image definition |
| **Compose file** | `.afb/generated/compose.yaml` | No | Generated multi-container orchestration |
| **Project config** | `.afb/project/` | Yes | Highest-priority layer |
| **External layers** | `.afb/layers/*/` | No | Cloned from git, gitignored |
| **Scripts** | `.afb/scripts/` | Yes | User shell scripts |

## Lifecycle States

A harness progresses through:

```
init → lock → apply → build → up
                ↑              ↓
                └── rebuild ←──┘
```

| State | Meaning |
|-------|---------|
| **Initialized** | Manifest exists, no lockfile or composed config yet |
| **Locked** | Lockfile generated, exact versions resolved |
| **Applied** | Layers composed, config translated to target formats |
| **Built** | Container image generated and built |
| **Running** | Container(s) up and accessible |

## Merge Semantics

| Structure | Behavior |
|-----------|----------|
| Object/map keys | Merge recursively. Incoming wins at leaf |
| Arrays | Replace — incoming replaces existing entirely |
| Scalars | Incoming wins |
| Key present in existing, absent in incoming | Preserved (no implicit deletion) |

**Priority**: layers sorted ascending by `priority` field. `.afb/project/` is implicit highest priority.

**Strategy**: per-layer override available. `merge` (default) or `overwrite` (all files in that layer replace rather than deep-merge).

## Architecture Terms

| Term | Definition |
|------|-----------|
| **Port** | Go interface defining how AFB interacts with an external dependency (git, container runtime, command executor). Defined where consumed |
| **Adapter** | Concrete implementation of a port (e.g., `GitCLI` implements the `Git` port by shelling out to the `git` binary) |
| **Core** | Pure domain logic — manifest parsing, layer composition, merge, Containerfile generation. No external dependencies |

## Container Terms

| Term | Definition |
|------|-----------|
| **Project container** | Container running the agent harness + project code. One per project |
| **Shared services** | MCP servers, databases running in their own containers, accessible to multiple project containers via compose networking. Managed by a separate shared-services manifest |
| **Compose project** | A named set of containers managed by a single compose.yaml. Named `afb-{dirname}` by default |
| **Named volume** | Docker/Podman volume that persists across container rebuilds. Used for auth tokens, MCP data |

## Conventions

- **Committed**: `afb.toml`, `afb.lock`, `.afb/project/`, `.afb/scripts/`
- **Gitignored**: `.ai/`, `.claude/`, `.opencode/`, `.mcp.json`, `.afb/layers/`, `.afb/generated/`, `afb.local.toml`
- **Inside container**: project code (cloned), `.ai/`, runtime configs, all component binaries
- **On host**: manifest, lockfile, AFB binary, container runtime

## Anti-definitions

Things AFB is NOT:

| Not this | That's the job of |
|----------|-------------------|
| Config translator | Sync command — LNAI (or successor) |
| Container orchestrator | podman-compose / docker-compose |
| Memory system | MCP servers (CASS, mcp-memory-service) |
| Agent orchestrator | Gas City (future) |
| Session manager | Runtime (Claude Code, OpenCode) |
