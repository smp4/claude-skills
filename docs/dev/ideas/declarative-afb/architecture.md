## Overview

AFB is a Go CLI that reads a TOML manifest (`afb.toml`) and orchestrates config composition, runtime sync, and component lifecycle. It is a thin coordinator — format translation is LNAI's job, orchestration is Gas City's job, memory is MCP servers' job. AFB's own logic: parse manifest, compose layers, shell out to tools, report results.

**Significant weakness of this approach**: AFB is a wrapper around wrappers. LNAI wraps runtime configs. AFB wraps LNAI. Each abstraction layer adds failure modes and debugging depth. Counterargument: each layer solves a distinct problem and can be removed independently. The risk of "abstraction fatigue" is real and must be managed by keeping AFB's scope minimal.

## Primitives

| ------------- | -------------------------------------------- | -------------------------------------------------------- | ---------------- |
| **Manifest**  | `afb.toml` — desired state declaration       | Yes (git)                                                | User             |

## Layer Composition Algorithm

```
COMPOSE(manifest):
    layers ← manifest.layers sorted by priority ASC
    target ← new empty temp directory

    FOR each layer in layers:
        dir ← .afb/layers/{layer.name}/
        IF dir not cloned:
            git clone layer.source → dir
        FOR each file in dir (recursive):
            dest ← target / relative_path(file)
            IF dest does not exist:
                copy file → dest
            ELSE:
                MERGE(dest, file, layer.strategy)

    # Project config is implicit highest priority
    FOR each file in .afb/config/ (recursive):
        dest ← target / relative_path(file)
        IF dest does not exist:
            copy file → dest
        ELSE:
            MERGE(dest, file, "merge")

    # Atomic replace
    remove .ai/ entirely
    move target → .ai/

MERGE(existing, incoming, strategy):
    IF strategy == "overwrite":
        replace existing with incoming
        RETURN
    # strategy == "merge" (default)
    ext ← file extension
    IF ext in {.yaml, .yml, .json, .toml}:
        deep_merge(existing, incoming)    # incoming wins at leaf
    ELSE:
        replace existing with incoming    # unstructured → overwrite
```

### Deep Merge Semantics

| Structure                                   | Behavior                                                      |
| ------------------------------------------- | ------------------------------------------------------------- |
| Object/map keys                             | Merge recursively. Incoming wins at leaf                      |
| Arrays                                      | **Replace** — incoming array replaces existing array entirely |
| Scalars                                     | Incoming wins                                                 |
| Key present in existing, absent in incoming | Preserved (no implicit deletion)                              |

Array append semantics are deferred (see spec unresolved questions). Replace is the safe default — it's predictable and avoids subtle duplication bugs.

```

    actual_ai ← current .ai/
```

### Command: `afb sync` (detailed)

```
1. Parse afb.toml
2. For each layer (by priority):
   a. If .afb/layers/{name}/ missing → git clone
   b. Optionally git pull (if --pull flag)
3. Run COMPOSE algorithm → writes .ai/
4. Shell out: sync command (default "lnai sync")
5. Log summary: layers composed, files written, targets synced
```

Exit codes: 0 = success, 1 = composition error, 2 = sync command error.

## Technology Choices

| Choice               | Rationale                                                                              |
| -------------------- | -------------------------------------------------------------------------------------- |
| **Go**               | Single binary, no runtime deps, fast startup, strong test stdlib. Aligns with Gas City |
| **cobra**            | Standard Go CLI framework for subcommands                                              |
| **BurntSushi/toml**  | Mature, well-tested TOML parser                                                        |
| **zerolog**          | Structured JSON logging, zero-allocation, 12-factor compatible                         |
| **gopkg.in/yaml.v3** | In-process YAML parse + merge (no yq dependency)                                       |
| **encoding/json**    | stdlib JSON parse + merge (no jq dependency)                                           |
| **git CLI**          | Shell out for clone/pull/push. Respects user's git config, SSH keys                    |

External runtime dependencies: `git`, configured sync command (default: `lnai`).

**Not using**: yq, jq (in-process merge avoids external tool deps), go-git (shell git is simpler and respects user config), template engines (simple string substitution suffices).

## Test Isolation Strategy

### Problem

Runtimes auto-discover config in well-known locations:
- Claude Code: `.claude/` in project, `~/.claude/` globally
- OpenCode: `.opencode/` in project, `~/.config/opencode/` (XDG)
- MCP servers: `~/.config/` or tool-specific paths

A test deployment can clobber production config.

### Strategy: HOME + XDG Override

```bash
export HOME=/tmp/afb-test-$(date +%s)
export XDG_CONFIG_HOME=$HOME/.config
export XDG_DATA_HOME=$HOME/.local/share
mkdir -p $HOME
cd $(mktemp -d)       # isolated project dir
# afb init && afb install && afb sync operate in isolation
```

In Go tests: `os.Setenv` before each test, `t.TempDir()` for project dirs. Tests are hermetic — no shared state between test cases.

### Alternatives (evaluate if HOME override insufficient)

| Approach       | Pros                                    | Cons                                                  |

Primary strategy: HOME/XDG override. Escalate to Devbox if tools ignore HOME. Containers for CI on the Linux box.

## Architecture Decision Records

### ADR-001: Go as implementation language

**Status**: Accepted
**Context**: Candidates were shell, Python, TypeScript, Go. User knows Python best. TypeScript aligns with LNAI ecosystem. Shell is fastest to prototype.
**Decision**: Go.
**Rationale**: Single binary (no runtime deps on target machines), fast CLI startup, strong test stdlib, aligns with Gas City (Go). User accepted trade-off of less familiarity for long-term fit.
**Consequences**: Need to learn Go idioms. Ecosystem tooling (cobra, zerolog, toml parser) is mature. Build produces a single distributable binary.

### ADR-002: LNAI for config translation, not Chezmoi or custom

**Status**: Accepted
**Context**: Chezmoi manages personal dotfiles (wrong abstraction — file copier, not format-aware translator). Custom canonical.toml + Jinja2 is a fragile SPOF. LNAI has per-runtime plugins that understand native formats.
**Decision**: Delegate config translation to LNAI. AFB composes layers; LNAI translates to runtime-native formats.
**Rationale**: LNAI solves the format translation problem correctly. Building our own translator is unnecessary custom work.
**Consequences**: Dependency on a 239-star project. Mitigated: coupling is a single configurable shell command (`[sync].command`), swappable without changing afb.
**Supersedes**: fusion_response.md proposal for Chezmoi + canonical.toml.

### ADR-003: Clone layers to .afb/layers/, not git subtrees or submodules

**Status**: Proposed (see Unresolved Question 3)
**Context**: Three options for external layer storage: git subtrees (pollute project history), git submodules (notoriously bad UX), git clones to a cache dir (clean but layers not in project git).
**Decision**: Clone to `.afb/layers/<name>/`, gitignored.
**Rationale**: Clean separation. No project history pollution. No submodule UX pain. afb manages clone/pull lifecycle via afb.toml declarations.
**Consequences**: Layers not browseable in GitHub project view. `afb layer pull` required after clone. Layer changes require `afb push` to propagate upstream.

### ADR-004: In-process deep merge via Go libraries, not yq/jq

### ADR-005: Shell out to git CLI, not go-git library

**Status**: Accepted
**Context**: Layer management requires git clone/pull/push. go-git is a pure-Go git implementation.
**Decision**: Shell out to the `git` CLI.
**Rationale**: Respects user's git config, SSH keys, credential helpers, GPG signing. Simpler than go-git. Smaller binary. git is a universal runtime dependency (already required by the projects afb manages).
**Consequences**: External dependency on `git` binary. Acceptable — any machine running AI coding tools already has git.

### ADR-006: Array replace, not append, as default merge strategy

**Status**: Accepted
**Context**: When merging structured files across layers, arrays (YAML lists, JSON arrays) could be replaced or appended.
**Decision**: Incoming array replaces existing array entirely.
**Rationale**: Replace is predictable and avoids subtle duplication bugs. Append semantics are ambiguous (what about duplicates? ordering? partial overlap?). If a layer wants to extend a list, it must include the full list.
**Consequences**: Layers that want to "add one item to a list" must duplicate the existing items. Trade-off: predictability over convenience. Append may be added later as an opt-in strategy.

### ADR-007: HOME/XDG override as primary test isolation

**Status**: Accepted
**Context**: Runtimes auto-discover config in `$HOME` and project dirs. Test deployments can clobber production. Alternatives: Devbox, containers, k8s.
**Decision**: Override `HOME`, `XDG_CONFIG_HOME`, `XDG_DATA_HOME` to temp dirs. Escalate to Devbox or containers if insufficient.
**Rationale**: Zero dependencies. Works for most tools. In Go tests, trivial via `os.Setenv` + `t.TempDir()`. Devbox/containers add complexity that may not be needed.
**Consequences**: Tools that hardcode paths (ignoring HOME) will break isolation. Must document exceptions per tool. OAuth tokens unavailable in test envs (validates config generation, not runtime auth).

### ADR-008: .afb/config/ as authored config, .ai/ as composed output

**Status**: Accepted
**Context**: LNAI reads from `.ai/`. If user authors config directly in `.ai/`, composition would overwrite their files. Need to separate authored vs generated.
**Decision**: User-authored project config lives in `.afb/config/` (committed). `.ai/` is composed output (gitignored, regenerated by `afb sync`).
**Rationale**: Clean separation — no ambiguity about what's authored vs generated. `.ai/` can be safely deleted and regenerated.
**Consequences**: Projects using vanilla LNAI (no afb) put config directly in `.ai/`. Migration path: `afb init` moves `.ai/` → `.afb/config/`. Adds one level of indirection vs vanilla LNAI.

### ADR-009: Integer priority in afb.toml, not directory-name ordering

**Status**: Accepted
**Context**: Original sketch used alphanumeric dir names (`01_base`, `02_team`) for layer ordering. Alternative: explicit integer priority field in afb.toml.
**Decision**: Mandatory `priority` integer field per layer in afb.toml. Higher wins.
**Rationale**: Decoupled from filesystem. No fragile naming conventions. Priority is explicit and inspectable in one place (afb.toml).
**Consequences**: User must assign priorities. Small cognitive overhead, but makes ordering unambiguous.

### ADR-010: Components as opaque lifecycle hooks

**Status**: Accepted
**Context**: Could type components (tool, mcp, skill) and have afb understand each type's semantics. Or treat all components identically — just lifecycle hook commands.
**Decision**: Components are opaque. afb runs hook commands (install, update, uninstall, backup, health) without understanding what the component is.
**Rationale**: Simplest possible design. No component taxonomy to maintain. Any tool with a CLI is manageable. User handles MCP config in their layer files.
**Consequences**: afb can't auto-configure MCP servers or validate component-specific config. User does this manually in `.afb/config/settings.yaml`. Acceptable for v1 — revisit if friction is high.

### ADR-011: Structured logging, not OpenTelemetry

**Status**: Accepted
**Context**: User asked if OTel is relevant. OTel is designed for distributed tracing across long-running microservices.
**Decision**: Structured JSON logs to stderr via zerolog. Log level via `AFB_LOG_LEVEL` env var.
**Rationale**: afb is a short-lived CLI process, not a distributed system. Structured logs with timestamps + levels + component fields provide sufficient observability. OTel would add significant dependency weight for no benefit.
**Consequences**: No distributed tracing. If Gas City adds long-running processes later, OTel could be evaluated for those — but that's Gas City's concern, not afb's.

### ADR-012: Sync command as configurable shell command

**Status**: Accepted
**Context**: afb needs to trigger config translation after composition. Could hard-depend on LNAI or make the sync tool configurable.
**Decision**: `[sync].command` in afb.toml (default: `"lnai sync"`). afb shells out to this command after composition.
**Rationale**: Minimal coupling. If LNAI is replaced, user changes one line in afb.toml. afb doesn't import LNAI, doesn't understand its API, doesn't break when LNAI changes internals.
**Consequences**: afb can't deeply validate sync results. Mitigated by `afb diff` which compares expected vs actual output regardless of sync tool.

### ADR-013: No Temporal, Redis, ChromaDB, MCP proxy

**Status**: Accepted
**Context**: fusion_response.md proposed Temporal + Redis + ChromaDB + Mem0 + MCP proxy. These are enterprise-scale tools.
**Decision**: Exclude all. Use lightweight alternatives at every layer.
**Rationale**: Temporal requires a database server (PostgreSQL/MySQL). Redis adds zero value at 2-10 agent scale (SQLite/filesystem sufficient). ChromaDB is redundant with mcp-memory-service. MCP proxy is unnecessary indirection (runtimes connect to MCP servers directly). All violate the "no database servers" constraint.
**Consequences**: If scale grows beyond 10+ agents on multiple machines, some of these decisions may need revisiting. Current constraint: solo dev, 1-2 Pro subs, 2 machines.
**Supersedes**: fusion_response.md infrastructure proposals.
